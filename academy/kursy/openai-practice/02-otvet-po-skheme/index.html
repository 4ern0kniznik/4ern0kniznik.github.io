Зачем это

Скрипту нужен не текст «Счёт № 214 на сумму…», а поля: номер, дата, сумма. Их кладут в таблицу, в 1С, в отчёт. Структурированный вывод (Structured Outputs) заставляет модель вернуть JSON строго по вашей схеме. Нет схемы — каждый ответ приходится разбирать регулярками и надеяться.

Урок

JSON-режим и строгая схема

Попросить модель «ответь в JSON» можно и в обычной подсказке. Она почти всегда послушается. «Почти» — проблема: то лишнее поле, то пропущенное, то комментарий перед JSON.

Строгий режим (strict: true) другой. Модель генерирует ответ так, чтобы он совпал со схемой JSON Schema: все обязательные поля на месте, типы верные, лишних полей нет. Это обещание формы, а не содержания. Схема гарантирует, что поле sum — число. Что число правильное, схема не гарантирует. Это проверяете вы.

В оригинале (2024 год) примеры написаны на Chat Completions, параметр там — response_format. Ниже — то же на Responses API, параметр называется text.format. Точный синтаксис сверяйте с документацией: он менялся.

Схема через Pydantic

Удобнее всего описать схему классом Pydantic. Библиотека openai сама переведёт его в JSON Schema и разберёт ответ обратно в объект.

python
from pydantic import BaseModel
from openai import OpenAI

MODEL = "..."  # актуальное имя модели — в документации OpenAI
client = OpenAI()

class Position(BaseModel):
    name: str        # наименование товара или услуги
    quantity: float
    price: float     # цена за единицу, ₽, без НДС

class Invoice(BaseModel):
    number: str
    date: str        # ДД.ММ.ГГГГ
    supplier: str
    positions: list[Position]
    total_without_vat: float
    vat: float
    total_with_vat: float

INSTRUCTIONS = (
    "Извлеки реквизиты счёта из текста письма. "
    "Дату пиши в формате ДД.ММ.ГГГГ. Суммы — числом, без пробелов и знака ₽. "
    "Если поля в письме нет, оставь пустую строку или 0."
)

LETTER = """Добрый день!
Направляем счёт № 214 от 28.10.2026 от ООО «Ладога-Снаб».
Бумага А4, 40 пачек по 350 руб. Картридж для принтера, 2 шт. по 4 100 руб.
Итого без НДС 22 200 руб., НДС 22 % — 4 884 руб., всего к оплате 27 084 руб."""

response = client.responses.parse(
    model=MODEL,
    instructions=INSTRUCTIONS,
    input=LETTER,
    text_format=Invoice,
)
invoice = response.output_parsed      # объект Invoice
print(invoice.number, invoice.date, invoice.total_with_vat)

output_parsed — уже объект Python, а не строка. Поля доступны через точку, типы проверены.

Схема вручную

Без Pydantic схему пишут словарём. В строгом режиме у схемы два обязательных условия: все поля перечислены в required, и у каждого объекта additionalProperties: false.

python
schema = {
    "type": "object",
    "properties": {
        "number": {"type": "string"},
        "date": {"type": "string", "description": "ДД.ММ.ГГГГ"},
        "total_with_vat": {"type": "number"},
    },
    "required": ["number", "date", "total_with_vat"],
    "additionalProperties": False,
}

response = client.responses.create(
    model=MODEL,
    instructions=INSTRUCTIONS,
    input=LETTER,
    text={"format": {"type": "json_schema", "name": "invoice", "schema": schema, "strict": True}},
)
import json
data = json.loads(response.output_text)

Поле description в схеме читает модель. Это место для коротких правил: формат даты, единица измерения, что писать при пустом значении.

Поле «необязательно» в строгом режиме делается так: оно остаётся в required, а тип — ["string", "null"]. Модель вернёт null, если значения нет.

Перечисления вместо свободного текста

Если у поля конечный список значений, задайте его через enum (в Pydantic — Literal или Enum). Модель не сможет вернуть «Бухгалтерия.» с точкой или «бух.». Это решает проблему из практики урока 1.

python
from typing import Literal

class Ticket(BaseModel):
    department: Literal["бухгалтерия", "склад", "ИТ", "договорной"]
    urgent: bool

Отказ

На вход скрипта может прийти что угодно, в том числе просьба, которую модель выполнять не станет. Тогда ответа по схеме не будет, а будет отказ (refusal) отдельным элементом ответа. Скрипт должен это заметить, а не упасть на разборе. В оригинале отказ показан на Chat Completions (поле refusal). В Responses API отказ приходит в содержимом сообщения с типом refusal; проверяйте output_parsed на None и смотрите response.output.

Практика Академии

Задача. Бухгалтерия получает счета в теле письма. Нужен скрипт, который превращает письмо в запись Invoice и сам проверяет арифметику.

Три тестовых письма (вымышленные поставщики):

текст
Письмо 1. Счёт № 88 от 01.11.2026, ООО «Ромашка-Сервис».
Уборка офиса за октябрь — 1 услуга, 18 000 руб. НДС не облагается. К оплате 18 000 руб.

Письмо 2. ООО «Вектор-Опт», счёт 1045 от 30.10.2026.
Стулья офисные — 6 шт. по 5 200 р. Стол — 1 шт., 12 800 р.
Без НДС 44 000 р., НДС 22 % 9 680 р., итого 53 680 р.

Письмо 3. Высылаем счёт от 3 ноября 2026 г. № 17/11 (ООО «Кедр»).
Вода питьевая 19 л — 10 бутылей по 420 руб. Аренда кулера — 1 мес., 600 руб.
Сумма без НДС 4 800 руб., НДС 1 056 руб., всего 5 856 руб.

Что сделать:

  1. Возьмите класс Invoice из урока, добавьте description к полям, где ошибается модель.
  2. Напишите функцию check(inv), которая возвращает список ошибок:
python
import re

def check(inv: Invoice) -> list[str]:
    errors = []
    if not re.fullmatch(r"\d{2}\.\d{2}\.\d{4}", inv.date):
        errors.append(f"дата не ДД.ММ.ГГГГ: {inv.date}")
    s = round(sum(p.quantity * p.price for p in inv.positions), 2)
    if s != round(inv.total_without_vat, 2):
        errors.append(f"позиции дают {s}, в счёте {inv.total_without_vat}")
    if round(inv.total_without_vat + inv.vat, 2) != round(inv.total_with_vat, 2):
        errors.append("без НДС + НДС ≠ итого")
    return errors
  1. Прогоните три письма, сравните с эталоном и выведите ошибки check.

Проверка:

  • все три записи совпадают с эталоном по шести полям таблицы;
  • check возвращает пустой список для всех трёх;
  • письмо 3: дата «3 ноября 2026 г.» превращена в 03.11.2026, номер «17/11» сохранён целиком;
  • испорченное письмо (поменяйте в письме 2 итог на 52 000 р.) даёт ошибку «без НДС + НДС ≠ итого». Модель не должна «исправлять» сумму сама: если исправила, допишите в инструкции «переписывай суммы как в письме, не пересчитывай».

Сравните модели

  1. Прогоните практику на двух-трёх значениях MODEL.
  2. У провайдеров с OpenAI-совместимым Chat Completions поддержка схем разная: у одних есть только «режим JSON» без строгой схемы, у других схема поддерживается частично. Проверьте по документации провайдера. Если строгой схемы нет, запросите JSON обычной подсказкой и разберите его тем же классом: Invoice.model_validate_json(text). Ошибка разбора тоже результат: запишите её.

Таблица для записи: модель, строгая схема есть или нет, сколько писем из трёх совпало с эталоном, сработала ли проверка на испорченном письме. Результатов прогона у нас нет, заполняете вы.
